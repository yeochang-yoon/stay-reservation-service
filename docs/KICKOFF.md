## 1. 서비스의 성격과 목표

국내 호텔·펜션형 숙박을 대상으로 여러 숙소 운영자가 상품과 판매 재고를 관리하고, 고객이 지역·날짜·인원으로 숙소를 찾아 예약·결제·취소·이용 후 리뷰까지 처리하는 독립적인 숙박 예약 웹서비스를 만든다.

Backend를 중심으로 재고·가격·예약·결제·권한 사이의 정합성을 다룬다. Frontend는 고객의 주요 흐름과 필요한 운영 작업을 실제로 수행·검증할 수 있는 수준으로 만들며 시각적 완성도는 후순위다. 야놀자 같은 서비스의 사업 문제를 참고하지만 특정 서비스의 화면·내부 구조를 복제하지 않는다.

예약 트랜잭션, JPA 비관적 락, 데이터 무결성, 예외 처리, 실제 DB 통합 테스트를 비즈니스 문제 해결의 근거로 설명할 수 있어야 한다. 개발·협업·Review·CI/CD·배포·운영·기존 서비스 변경까지 [개발 절차](DEVELOPMENT_PROCESS.md)의 전체 Lifecycle을 유지한다.

### 이전 안이 과도하게 축소된 이유

이전 안은 예약·락 학습을 빨리 시작하기 위해 실물 객실 1개, 결제 없는 즉시 확정, 초기 데이터만으로 범위를 좁혔다. 이 모델 자체는 개별 숙소의 단순 예약에는 가능하지만, 이번 프로젝트에서는 타입별 수량 경쟁·여러 숙박일의 재고 처리·공급자 운영·가격 및 결제 상태 불일치 문제가 사라졌다.

개발 작업의 자동화 요청을 도메인 축소의 근거로 사용한 것이 문제였다. 이번 개정에서는 핵심 도메인을 유지하고, 반복 작업 자동화·기능별 개발·단순한 초기 정책과 화면으로 개발 비용을 관리한다.

## 2. 공개 서비스 자료에서 확인한 도메인과 적용 범위

Booking.com은 재고와 검색 조건에 따른 예약 가능 여부를 구분하며, 객실 타입·날짜별 잔여 수량과 판매 중지를 다룬다. 이 자료를 근거로 우리 서비스도 객실 타입별 날짜 재고와 판매 가능 여부를 핵심으로 제안한다. [재고와 예약 가능 여부](https://developers.booking.com/connectivity/docs/ari), [날짜별 판매 재고](https://developers.booking.com/connectivity/docs/b_xml-roomrateavailability).

검색에는 지역·숙박 날짜·인원·객실 조건이 사용되고, 예약 생성 전 가격·재고·조건을 다시 확인하는 단계가 공개돼 있다. 우리 서비스에서는 지역·날짜·인원 검색과 예약 직전 재검증을 첫 버전에 포함하도록 제안한다. [숙박 검색](https://developers.booking.com/demand/docs/accommodations/search-for-available-properties), [예약 전 확인과 생성](https://developers.booking.com/demand/docs/orders-api/order-preview-create).

결제의 중복 요청과 응답 유실은 별도의 문제다. 토스페이먼츠는 멱등키를 통한 재시도를 설명하며 테스트용·실거래용 키도 구분한다. 이를 참고해 결제 재시도와 실제 금전 거래 여부를 범위 결정에 포함했다. [결제 요청의 멱등성](https://docs.tosspayments.com/reference/using-api/authorization), [테스트·실거래 키](https://docs.tosspayments.com/reference/using-api/api-keys).

위 자료는 외부에 공개된 기능·도메인 개념의 근거다. 특정 회사의 내부 DB, 트랜잭션, 락 구조를 확인한 것은 아니다. 아래 서비스 범위와 검증 기준은 이 프로젝트에 대한 제안이며 문서의 구조나 정책을 그대로 채택한 것이 아니다.

## 4. 실제 사용자 시나리오 — 제안

1. 숙소 관리자가 숙소와 객실 타입을 등록하고 정원·공급 수량·날짜별 판매 재고·가격을 설정해 판매를 시작한다. 초기 데이터는 개발 보조로만 사용한다.
2. 고객이 지역, 체크인·체크아웃, 인원을 입력한다. 전체 숙박 기간에 판매 가능한 객실 타입과 해당 조건의 총액을 비교한다.
3. 고객이 객실 타입을 선택하고 가격 내역·인원 조건·취소 조건을 확인한다. 검색 후 가격이나 재고가 바뀌었으면 예약 전 다시 안내받는다.
4. 로그인한 고객이 예약을 요청한다. 판매 수량 범위에서 필요한 날짜의 재고를 확보하고 결제 대기 상태로 진행한다. 결제 결과와 정합성이 확인된 예약만 확정된다.
5. 결제 실패·이탈·대기 만료 시 예약과 재고가 정리된다. 재시도나 중복 알림으로 결제·확정·재고 복원이 두 번 일어나지 않는다.
6. 고객이 본인 예약과 결제 상태를 확인하고 취소 조건에 따라 취소한다. 수수료·환불 결과와 재판매 가능한 재고가 일관되게 반영된다. 환불 실패는 성공으로 숨기지 않고 조치할 수 있다.
7. 숙소 관리자가 실제 이용과 미이용을 구분해 기록한다. 이용 완료한 고객은 리뷰를 남기며 숙소의 평균 평점에 반영된다.
8. 운영자는 예약·재고·결제 불일치나 실패 처리를 조회하고 기록된 근거로 복구한다. 배포 이후에도 기존 예약과 이력을 유지하며 서비스를 변경한다.

이는 사용자 흐름의 제안이다. 상태 이름·세부 전이·만료 시간·취소 요율·이용 완료 판정 규칙은 다음 요구사항 단계에서 확정한다.

## 6. 예약·재고·가격·취소·리뷰에서 남겨야 할 문제

### 객실 타입과 실제 객실 관리

추천 모델은 객실 타입별 수량 판매다. 예를 들어 같은 조건의 디럭스 객실 여러 개를 하나의 타입으로 판매하되 날짜마다 판매 가능 수량이 달라질 수 있다. 재고는 이 서비스에서 판매하도록 배정된 수량이며 다른 판매 채널의 재고까지 자동으로 보장한다고 가정하지 않는다.

첫 버전은 같은 타입의 객실을 교환 가능한 공급으로 취급한다. 특정 호실 지정, 청소·정비 일정, 객실 이동과 호실별 배정은 PMS 영역으로 후속 확장한다. 다만 공급 수량과 날짜별 판매 제한을 관리하는 기능은 처음부터 포함한다. 객실 타입 안에서도 호실별 연속 투숙 가능성이 다른 상품은 이 모델의 지원 대상이 아니다.

### 날짜 재고와 경쟁

여러 박 중 하루라도 재고가 부족하면 전체 예약이 성립할 수 없어야 한다. 결제 대기 중인 재고도 판매 가능량에 영향을 주며, 확정·실패·만료·취소 이후 수량이 일관되어야 한다.

같은 타입의 예약 기간이 겹치는 것 자체는 오류가 아니다. 판매 수량을 초과한 예약이나 동일 요청의 중복 처리를 막아야 한다. 예를 들어 필요한 세 날짜의 판매 가능 수량이 각각 3·2·4개라면 해당 기간에 새로 판매할 수 있는 객실은 최대 2개다. 이는 다박 재고 문제를 설명하는 예시이며 실제 날짜 경계와 선점 정책은 요구사항에서 정한다.

고객끼리 마지막 수량을 경쟁하는 경우뿐 아니라, 관리자 재고 감소와 예약, 만료와 결제 성공, 취소와 중복 환불 요청이 겹치는 경우도 다룬다. JPA 비관적 락의 대상·범위·순서와 DB 제약은 설계 단계에서 결정하고 모든 관련 변경 경로에 대한 정합성을 검증한다.

### 가격과 검색 결과의 유효성

첫 버전은 객실 타입별 기본 판매 조건 한 세트, 날짜별 금액과 추가 인원 요금을 지원하도록 추천한다. 전체 숙박료와 필수 추가 비용을 고객이 확인할 수 있어야 하며, 서버가 계산한 금액과 승인 대상 금액이 일치해야 한다.

관리자가 요금·취소 조건을 바꾸더라도 이미 성립한 예약의 계약 내용이 바뀌면 안 된다. 검색 가격이 달라졌을 때 고객에게 재확인받는 기준, 견적의 유효성, 금액 계산·반올림·날짜 경계는 다음 단계에서 정한다.

### 예약·결제·취소의 서로 다른 상태

예약 취소 요청, 재고 반환, 환불 완료는 같은 사실이 아니다. 외부 처리 실패나 응답 유실이 있어도 중간 상태와 조치 근거를 남기고 일관된 결과로 수렴해야 한다. DB Rollback만으로 이미 성공한 외부 결제를 되돌릴 수 있다고 가정하지 않는다.

취소 가능 기한과 시점에 따른 수수료·환불을 포함하되, 첫 버전은 단순한 기본 정책부터 시작한다. 정확한 정책, 재고 반환 시점, 재시도·보상·운영 복구 절차는 요구사항과 설계에서 결정한다.

### 실제 이용과 리뷰 신뢰성

예약 확정 또는 체크아웃 예정일 경과만으로 실제 숙박을 했다고 단정하지 않는다. 숙소 관리자의 이용 상태 기록과 노쇼 구분을 포함하고, 이용 완료한 본인의 예약과 리뷰를 연결하도록 추천한다.

리뷰 작성·변경·삭제와 공개 상태가 평균 평점에 어떻게 반영되는지 정의하고 검증한다. 서비스 관리자의 기본 비공개 조치·이력은 운영 범위에 포함하되, 신고 심사·분쟁 포털 전체는 후속으로 둔다.

## 7. 결제 범위 선택

| 선택 | 성립하는 서비스 | 유지·추가되는 문제 | 한계와 판단 |
| --- | --- | --- | --- |
| 온라인 결제 제외·현장결제 | 현장결제 조건의 숙박 예약 | 예약·재고·취소·노쇼를 여전히 다뤄야 함 | 현실적인 사업 모델이지만 온라인 승인·환불·결제 대기의 정합성은 배우지 못함. 이번 목표에는 비추천 |
| 자체 모의 결제 | 실제 금전 이동 없이 결제·예약 전 과정을 체험하는 서비스 | 성공·거절·지연·응답 유실·중복 통지·취소 실패를 재현하고 선점·만료·재처리를 검증 | 실패를 통제해 재현하기 좋으나 실제 PG 인증·네트워크 연동은 검증하지 못함. 외부 연동을 후속으로 둘 경우의 대안 |
| PG 테스트 환경 | PG의 테스트 승인·취소·알림을 연동한 체험 서비스 | 실제 외부 API·인증·웹훅 처리 경험, 재고·결제 정합성 문제 | 외부 의존·키·연동 작업이 추가됨. 실제 연동을 경험하되 실금전 이동을 제외할 수 있어 **첫 버전 추천**. 통제하기 어려운 실패는 자동화 검증용 모의 응답을 병행 |
| PG 실결제 | 실제 금전이 이동하는 숙박 거래 | 실승인·환불·대사·정산, 사업자 및 실제 공급 운영 준비 | 첫 버전에서 제외 추천. 테스트 연동과 운영 절차 검증 후 별도 도입 판단 |

추천은 **PG 테스트 연동과 통제 가능한 모의 응답 테스트의 병행**이다. 전자는 실제 외부 승인·조회·취소·알림 연동을 확인하고, 후자는 재현하기 어려운 지연·중복·응답 유실·취소 실패를 반복 검증한다. 모의 응답은 자동화 검증 수단이며 이를 PG 연동 성공의 근거로 대신하지 않는다. 단순히 같은 예약 트랜잭션 안에서 무조건 성공을 반환하는 함수로 끝내지 않는다.

테스트 화면에도 실제 금전이 이동하지 않음을 표시한다. 실승인·실환불·상업 정산까지 검증한 서비스라고 표현하지 않는다. 결제 시도·금액 검증·취소/환불·멱등 처리와 실패 복구는 첫 버전에 포함한다. PG 사업자·지원 테스트 결제수단·키 접근 조건·알림 검증 및 구체적인 연동 구조는 설계에서 확인·결정한다. 특정 PG는 아직 선택하지 않았다.

## 8. 첫 번째 버전과 후속 버전의 경계 — 추천안

첫 버전은 **공급자가 판매를 준비하고 고객이 조건 검색 → 견적 확인 → 예약·PG 테스트 결제 → 예약 관리·취소 → 실제 이용 기록 → 리뷰를 남기는 흐름**을 완성한다. 국내·원화·박 단위 숙박, 예약 1건에 객실 타입 하나의 객실 1개를 기본 범위로 추천한다. 판매 재고는 타입별 여러 개이며 단일 실물 객실 모델로 돌아가지 않는다.

고객 화면과 숙소 관리자의 핵심 입력·조회 화면은 제공한다. 서비스 관리자의 제한된 운영 기능은 우선 API와 실제 요청 검증으로 제공하고 필요한 최소 화면을 추가한다. API만 완성하고 전체 웹서비스를 완료 처리하지 않는다.

| 후속으로 미루는 기능 | 제외로 발생하는 제한과 이유 | 이후 도입 방식 |
| --- | --- | --- |
| 호실 지정·배정·청소·정비 PMS | 고객이 특정 호실을 지정할 수 없고 개별 객실 운영을 통합하지 않음. 타입별 공급 판매에 집중 | 물리 객실과 배정·정비 업무를 추가하고 기존 예약과 이관·호환성 검증 |
| 여러 객실·여러 타입 일괄 예약 | 단체 예약과 장바구니가 없음. 단일 객실 예약만으로 일반 고객 흐름은 성립 | 예약 내 여러 상품·재고의 일괄 확보 및 부분 실패/취소 요구사항 추가 |
| 여러 요금제·쿠폰·프로모션·동적 가격 | 조식 포함/불포함·환불형/불가형 상품을 동시에 비교하지 못함. 날짜·인원별 가격 자체는 포함 | 공유 재고에 여러 판매 조건을 연결하고 할인 우선순위·기존 계약 보존 검증 |
| 아동 연령별 할인·영유아 무료·추가 침구 | 첫 버전은 모든 투숙객을 정원에 포함하고 동일한 인원 요금 기준 적용 추천. 할인·수용 조건을 안내해야 함 | 인원 구성·연령·요금·정원 정책을 함께 확장. 인원 검증 자체는 현재 포함 |
| 해외·다중 통화·대실 | 해외 시간대·환율·시간 단위 재고를 지원하지 않음. 박 단위 예약과 날짜 가격에 집중 | 통화·시간대·예약 시간 단위 요구사항과 데이터 이관 영향 분석 |
| 외부 채널·PMS 연동 | 외부 플랫폼의 판매·취소가 자동 반영되지 않음. 본 서비스에 배정된 재고만 보장 | 채널별 배정·동기화·대사·외부 이벤트 중복/순서 역전 처리 추가 |
| PG 실결제·정산·분쟁 자동화 | 실제 금전 수취·공급자 정산·자동 분쟁 해결은 못함. PG 테스트 승인·환불·실패 조치와 상태 대조는 포함 | 테스트 연동·대사·복구 검증 후 운영 준비와 실거래 도입을 별도 판단 |
| 소셜 로그인·비밀번호 복구 메일·알림 | 계정 복구·외부 알림 편의는 제한. 계정 보안과 사이트 내 상태 조회는 포함 | 계정 소유 확인·알림 실패·재시도 정책을 추가. 초기 운영에서는 관리자도 비밀번호를 알 수 없게 함 |
| 추천·지도·사용자 파일 업로드·상세 관제 | 탐색 편의·콘텐츠·대규모 관측 기능 제한. 지역·날짜·인원 검색과 로그·Health는 포함 | 실제 사용·운영 문제를 근거로 순차 도입. 기본 이미지는 관리 가능한 URL/정적 자산으로 제공 |

첫 버전의 운영 기본값에는 데이터 Migration, 기존 예약·결제 이력 보존, 주요 관리자 변경 이력, 명확한 오류 응답, 권한 검증, 비밀번호 보호와 민감정보 로그 제외를 포함한다. 판매 중지나 정보 변경으로 기존 예약·리뷰·금액 근거가 사라지지 않아야 한다. 구체적인 데이터 보존·탈퇴 정책은 요구사항에서 확정한다.

## 9. 핵심 기능 완료를 판단할 검증 기준

아래는 **향후 구현의 수용 기준 제안**이다. 현재는 Kickoff 문서 단계이므로 실행된 기능 Test 결과가 아니다.

| 검증 영역 | 실제로 확인할 결과 |

| 공급 운영 | 관리자가 숙소·타입·정원·수량·날짜별 재고·가격을 관리하면 고객 검색·견적에 반영됨. 다른 숙소 관리자는 변경 불가 |

| 동시 예약 | 실제 RDBMS와 독립 트랜잭션으로 겹치는 다박 요청을 동시에 실행. 판매 가능 수량을 넘는 선점·확정이 없고 통제된 조건에서 성공 건수·거절 사유·DB 잔여량이 기대값과 일치 |
| 전체 기간의 원자성 | 일부 숙박일의 재고만 차감된 예약이나, 실패 후 남은 선점이 없음. 겹치지 않는 기간·다른 타입도 정상 처리 |
| 관리 작업과 경쟁 | 재고 감소·판매 중지와 예약이 겹쳐도 이미 확보한 수량을 침해하거나 덮어쓰지 않음. 기존 계약 보존 |
| 결제·만료 경쟁 | 성공/실패/응답 유실·지연·중복·만료 후 도착을 재현하고, 이중 결제·이중 확정·초과 판매 없이 정해진 결과로 수렴. 인프라 오류와 재고 부족을 구분 |
| 취소·환불 | 시점별 환불액·수수료 일치, 중복 취소와 재시도에도 재고·환불 한 번만 반영. 환불 실패 기록과 재처리·운영 조치 검증 |
| 이용·리뷰 | 미이용·노쇼·타인 예약·중복 리뷰 차단. 이용 완료와 작성 자격 연결, 리뷰 변경/비공개 후 평균 평점 일관성 |
| 보안·예외 | 본인/담당 숙소 권한, 관리자 권한 획득 통제, 금액 위변조·잘못된 입력·허용되지 않은 상태 변경 차단. 오류 응답과 로그에 민감정보 노출 없음 |
| 전체 서비스 | 배포된 화면에서 공급 준비·검색·예약·PG 테스트 결제·취소·이용 후 리뷰를 수행하고 DB·로그·Health로 결과 확인. 외부 연동 결과와 자동화 검증의 모의 응답 결과를 구분. CI와 데이터 유지 Migration·재배포까지 검증 |

경쟁 테스트에는 시작 조건·초기 재고·요청 수·트랜잭션 분리·성공/실패 건수·최종 DB 상태를 남긴다. 반복 실행으로 검증하고 단순 Mock Test나 코드 검토만으로 동시성을 보장했다고 판단하지 않는다. 시간 경계·대기 만료·이용 완료는 시간을 통제해 재현할 수 있어야 한다.

## 10. Kickoff에서 결정할 것과 이후에 결정할 것

지금 검수할 핵심은 다음 범위다.

- 객실 타입별 날짜 수량 판매, 검색·가격·재고·운영자 관리·상태 전이·이용 연계 리뷰를 첫 버전에 포함한다.
- 결제는 PG 테스트 연동을 추천하고 실패 조건을 반복 재현하는 모의 응답 테스트를 병행한다. 자체 모의 결제만으로 첫 버전을 구성하는 것은 대안이다.
- 국내·원화·박 단위·예약당 객실 1개·단순한 초기 요금/취소 정책을 경계로 하고 핵심 도메인은 유지한다.
- 호실별 PMS·다중 객실 일괄 예약·다중 요금제·실결제/정산·외부 채널 연동은 위 제한과 도입 경로를 전제로 후속으로 둔다.

구체적인 날짜 경계, 인원·아동 정책, 요율·세금/필수 비용 표시 방식, 취소 기한·수수료, 선점 만료 시간, 상태 전이표, 이용·노쇼·리뷰·탈퇴 규칙은 요구사항 단계에서 확정한다. 위 표의 제안을 세부 Business Rule 확정으로 해석하지 않는다.

ERD·API 계약·DB/Build Tool 선택·트랜잭션 경계·락 대상과 순서·배치/복구 구조·검색 구현·평점 저장 방식은 초기 설계 또는 해당 기능 설계에서 결정한다. 지금 특정 아키텍처나 추가 인프라를 미리 도입하지 않는다.

## 11. 완료 조건과 다음 작업

서비스 대상, 역할, 정상·실패 시나리오, 첫 버전 포함/제외 범위와 이유, 확장 경로, 검증 목표를 사용자가 검수하고 범위를 확정해야 Kickoff를 완료 처리한다.
