# Project Kickoff — 숙박 예약 서비스

범위 확정: 2026-10-19 사용자 승인. 상세 정책·수치·수용 기준의 원본은 [REQUIREMENTS.md](REQUIREMENTS.md)다.

## 목적과 서비스 성격

국내 호텔·펜션형 숙박을 대상으로 여러 숙소 운영자가 상품과 판매 재고를 관리하고 고객이 숙소를 찾아 예약·결제·취소·이용 후 리뷰까지 수행하는 독립적인 숙박 예약 웹서비스를 만든다. 실제 플랫폼의 비즈니스 문제를 참고하되 특정 서비스의 화면이나 내부 구조를 복제하지 않는다.

Backend의 예약·재고·가격·권한·데이터 정합성을 중심으로 문제 해결 근거를 설명할 수 있는 결과를 목표로 한다. Frontend는 고객과 운영자의 핵심 업무를 실제 이용·검증할 수준으로 만들며 시각적 완성도는 후순위다.

핵심 기술 학습 목표는 예약 트랜잭션, JPA 비관적 락과 실제 DB 동시성 통합 테스트를 비즈니스 정합성 문제에 연결해 검증하고 설명하는 것이다.

반복 작업 자동화로 개발 효율을 높이며 핵심 도메인을 축소하지 않는다. 전체 개발·협업·검증·CI/CD·배포·운영·기존 서비스 변경은 [개발 절차](DEVELOPMENT_PROCESS.md)를 따른다.

## 주요 사용자

| 사용자 | 핵심 업무 |
| --- | --- |
| 비회원 | 숙소·상품·가격·후기 탐색, 회원 가입 |
| 일반 회원 | 예약·결제, 본인 예약 관리·취소, 이용 후 리뷰 |
| 숙소 관리자 | 담당 숙소·타입·공급·요금·판매 상태와 예약·이용 관리 |
| 서비스 관리자 | 관리자 자격·담당 숙소 연결과 필요한 운영 조치 |

역할별 정확한 권한·입력과 예외의 원본은 요구사항 문서다.

## 핵심 사용자 흐름

1. 공급자가 숙소·객실 타입을 등록하고 날짜별 재고와 가격을 설정해 판매한다.
2. 고객이 지역·숙박 날짜·인원으로 판매 가능한 상품과 전체 가격을 비교한다.
3. 조건을 확인한 고객이 예약하고 PG 테스트 결제를 진행한다.
4. 결제 대기·성공·실패·만료를 확인하고 본인의 예약을 관리한다.
5. 취소 시 비용·환불과 재고 반환 상태를 확인한다.
6. 관리자가 실제 이용을 기록하고 이용 고객이 리뷰를 작성한다.
7. 운영자가 실패 거래를 조사·조치하고 기존 데이터를 유지하며 서비스를 변경한다.

정상·실패·경쟁·시간 경계의 세부 흐름과 판단 기준은 요구사항에서 관리한다.

## 첫 번째 서비스 버전에 포함할 범위

| 영역 | 포함 범위와 이유 |
| --- | --- |
| 상품·공급 | 숙소·객실 타입별 다수 수량, 날짜별 재고·판매 중지. 실제 공급자가 판매를 운영할 수 있어야 함 |
| 검색·가격 | 지역·날짜·인원 검색, 날짜·인원별 가격과 전체 숙박료, 예약 당시 조건 보존. 투숙 가능한 상품을 구매 판단할 수 있어야 함 |
| 예약·결제·취소 | 선점·결제·확정·만료·취소·환불 정합성. 실패와 재시도에도 거래·재고가 일관되어야 함 |
| 공급자·권한 | 숙소 관리자의 핵심 관리 기능과 화면, 최소 서비스 관리자 기능과 API 검증. 본인·담당 숙소 경계를 보장해야 함 |
| 이용·리뷰 | 실제 이용과 후기 자격 연결, 리뷰와 평균 평점. 미이용·중복 평가를 통제해야 함 |
| 운영·검증 | 예외·보안·변경 이력·Migration·복구·로그·Health와 실제 DB 통합/동시성 테스트. 운영 가능한 근거를 남겨야 함 |
| 사용자 화면 | 고객·숙소 관리자의 주요 흐름을 실제 이용. Backend API만으로 전체 웹서비스를 완료하지 않음 |

초기 경계는 국내·원화·박 단위 숙박, 예약당 한 타입의 객실 1개, 단순한 초기 요금·취소 정책이다. 타입별 판매 수량은 여러 개이며 단일 실물 객실의 중복 여부만 다루는 모델로 축소하지 않는다.

결제는 **PG 테스트 연동 + 실패 재현용 모의 응답 테스트**를 병행한다. 특정 PG와 연동 방식은 아직 선정하지 않았으며, 실제 지원·접근 조건을 확인한 뒤 설계한다. 상세 선정 조건의 원본은 요구사항의 PG-GATE다.

## 후속 버전의 범위와 제한

| 후속 기능 | 첫 버전의 제한·판단 근거 | 이후 도입 경로 |
| --- | --- | --- |
| 호실 배정·청소·정비 PMS | 타입 안의 객실은 교환 가능한 공급. 특정 호실·호실별 연속 투숙을 지원하지 않음 | 물리 객실·배정·정비와 기존 예약의 호환성 검토 |
| 여러 객실·타입 일괄 예약 | 단체/장바구니가 없음. 단일 객실 고객 흐름은 성립 | 여러 재고 확보·부분 실패/취소 추가 |
| 여러 요금제·프로모션·동적 가격 | 날짜·인원별 가격은 포함하되 요금제/할인의 복합 비교는 제외 | 공유 재고·판매 조건·할인 우선순위 확장 |
| 아동 연령별 할인·추가 침구 | 연령별 요금·수용 상품을 지원하지 않음. 정원·기본 인원 정책은 요구사항에서 정함 | 인원 구성·정원·요금 정책을 함께 확장 |
| 해외·다중 통화·대실 | 국내 박 단위 상품에 집중 | 시간대·통화·시간 단위 재고 도입 |
| 외부 채널·PMS 연동 | 본 서비스에 배정된 재고만 보장 | 채널 배정·동기화·대사와 외부 이벤트 처리 |
| 실결제·정산·분쟁 자동화 | 실제 금전 거래·정산은 제외. 테스트 환불·기본 운영 조치는 포함 | 테스트 근거·상용 조건·대사/복구 확인 후 별도 결정 |
| 소셜 로그인·복구 메일·알림 | 계정·외부 알림 편의 제한. 보안과 사이트 내 상태 조회는 포함 | 소유 확인·전송 실패·재시도 정책 추가 |
| 추천·지도·사용자 파일 업로드·고급 관제 | 기본 탐색·관리와 운영 근거에 집중 | 실제 사용자/운영 문제에 맞춰 도입. 기본 이미지는 관리 가능한 참조/정적 자산 사용 |

## 이후 단계로 인계할 사항

상세 Business Rule과 수용 기준은 [REQUIREMENTS.md](REQUIREMENTS.md), 실제 기술·도메인 구조·ERD·API·트랜잭션·락은 이후 설계 문서에서 결정한다. 현재 진행 위치와 미해결은 [PROJECT_STATE.md](PROJECT_STATE.md)에 둔다.
