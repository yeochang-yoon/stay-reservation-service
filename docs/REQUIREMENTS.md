# MVP 요구사항 — 정책 검수 초안

작성일: 2026-10-19 (Asia/Seoul)

상태: **Phase 2 / MVP 요구사항 정의 진행 중**. [Kickoff](KICKOFF.md)의 서비스 범위는 사용자 승인으로 확정됐다. 이 문서의 세부 Business Rule·수치·상태 전이·수용 기준은 검수 초안이며 아직 확정하지 않았다. 정책 검수·필수 값 확정·설계 준비 조건을 충족하기 전 요구사항 완료로 처리하지 않는다.

## 1. 승인된 범위와 이번 문서의 경계

확정 범위는 숙소·객실 타입별 다수 재고, 날짜별 판매 재고, 지역·날짜·인원 검색과 가격, 예약·결제·취소, 공급 관리와 권한, 이용·리뷰, 동시성·데이터 무결성 검증이다. 국내·원화·박 단위·예약당 한 타입의 객실 1개·단순한 초기 요금/취소 정책으로 시작한다.

PG 테스트 환경 연동과 실패 재현용 모의 응답 테스트를 병행한다. PG 사업자·결제수단·승인/조회/취소/알림 방식과 제약은 실제 지원·접근 조건 확인 후 설계 단계에서 선택한다. 이 문서의 업무상 요구를 특정 PG가 이미 지원한다고 해석하지 않는다.

호실별 PMS, 다객실 일괄 예약, 다중 요금제, PG 실결제·정산, 외부 채널 연동 등 후속 범위는 Kickoff의 제외 이유와 확장 경로를 따른다. DB·ERD·API·트랜잭션·락·배치 구조는 이번 문서에서 선택하지 않는다.

## 2. 용어와 범위에서 직접 도출되는 필수 조건

- 객실 타입: 한 숙소 안에서 동일 조건의 객실들을 수량으로 판매하는 단위. 한 타입 안의 객실들은 교환 가능한 공급으로 취급한다.
- 날짜별 공급량: 그 날짜에 이 서비스에 배정한 해당 타입의 판매 한도. 실제 전체 객실 수와 다른 채널의 판매 수량을 혼동하지 않는다.
- 선점: 결제 대기를 위해 한시적으로 확보한 공급. 확정으로 전환할 때 같은 수량을 두 번 차감하지 않는다.
- 예약 가능 여부: 숙소·타입의 판매 상태, 각 숙박일 재고, 정원, 적용 가격과 요청 조건을 함께 충족하는지 판단한 결과.
- 견적: 선택한 날짜·인원에 대한 가격 내역과 취소 조건. 견적 조회 자체는 재고 확보나 예약 확정이 아니다.
- 예약·결제·이용 상태: 서로 다른 업무 사실이다. 결제 화면 이동 성공이나 예정 퇴실일 경과만으로 예약 확정·이용 완료를 판단하지 않는다.
- 계약 내용: 예약 당시 확정한 숙소·타입 표시 정보, 날짜·인원, 박별 금액·총액, 적용 취소 조건과 변경 이력. 이후 상품 변경으로 덮어쓰지 않는다.

핵심 불변 조건은 다음과 같다. 저장 구조나 락 구현 방식의 확정은 아니다.

| ID | 반드시 지킬 결과 |
| --- | --- |
| INV-01 | 각 숙박일의 유효 선점과 확정 예약이 공급 한도를 넘거나 잔여량을 음수로 만들지 않음 |
| INV-02 | 한 예약의 전체 숙박일 재고가 확보되거나 전혀 확보되지 않음. 일부 날짜만 남는 실패는 허용하지 않음 |
| INV-03 | 같은 업무 요청의 재시도·중복 통지가 예약 확정·수량 전환/복원·환불을 중복 수행하지 않음 |
| INV-04 | 가격·공급·판매 상태 변경이 이미 성립한 계약과 확보 수량을 조용히 훼손하지 않음 |
| INV-05 | 결제 확인 금액·통화·예약 연결이 일치해야 확정할 수 있고, 불확실한 결과는 성공/실패로 꾸미지 않음 |
| INV-06 | 예약 취소와 환불 완료를 구분하고, 실패·미해결 상태와 재처리 근거를 남김 |
| INV-07 | 본인·담당 숙소·서비스 관리자 권한을 모든 변경 경로에서 확인함 |
| INV-08 | 거래·주요 관리 변경 이력과 리뷰/평점의 일관성을 유지하며 승인 없는 데이터 삭제로 문제를 해결하지 않음 |

## 3. 정책 검수 목록

**POL-01~POL-12는 전부 사용자 검수 대기**다. 추천안은 비교 가능한 초안이며 구현 기본값으로 확정하지 않는다. 추천안의 구조 승인과 미정 수치의 승인은 별개다.

| 정책 | 추천안 | 대안과 trade-off |
| --- | --- | --- |
| POL-01 날짜·예약 기간 | 한국 시간의 달력 날짜로 체크인 포함·체크아웃 제외. 숙소별 입실/퇴실/입실 마감 시각 관리. 당일 예약은 입실 마감 전만 허용. 최소 1박, 최대 30박·180일 이내 판매를 초기 한도 후보로 제안 | 당일 예약 제외는 단순하지만 당일 수요를 잃음. 장기/먼 미래 예약 허용은 판매 범위가 늘지만 가격·재고 준비와 취소 리스크 증가. 한도와 숙소 기본 시각은 미확정 |
| POL-02 인원·예약자 | 모든 투숙객을 최대 정원에 포함하고 기준 인원 초과분에 같은 추가 요금 적용. 첫 버전은 회원이 대표 투숙객인 예약부터 지원 | 아동/영유아 차등 정책·타인 명의 예약은 현실성이 늘지만 나이·대표자·동의·요금 정책이 추가됨. 연령/입실 제한과 최소 수집 정보는 추가 검수 필요 |
| POL-03 공급 변경 | 공급량을 유효 선점+확정 수량보다 낮출 수 없음. 판매 중지는 신규 선점을 막되 기존 선점은 유효기간 안에 완료 가능. 기존 계약 강제 취소는 별도 업무 | 판매 중지 시 기존 선점도 무효화하면 긴급 중단은 쉽지만 결제 진행 고객의 보상·환불과 안내가 증가 |
| POL-04 견적·가격 고정 | 예약 생성 시 서버가 현재 가격·조건을 재검증. 증감 어느 쪽이든 달라졌으면 재동의 후 진행. 유효 선점 이후에는 그 가격·취소 조건을 기한까지 고정. 원 단위 정수·필수 비용 포함 총액 표시. 확정 후 날짜/타입/인원 변경은 취소·재예약으로 처리 | 가격 하락 자동 적용은 편하지만 동의한 내용과 달라짐. 견적부터 가격 보장은 보장 기간이 필요. 기존 예약 직접 변경은 새 재고·가격 확보와 차액 처리 필요. 취소·재예약은 취소 비용·새 예약 실패 위험을 먼저 안내해야 함 |
| POL-05 선점·만료 | 생성 시 10분의 고정 결제 대기, 재시도나 화면 새로고침으로 연장하지 않음. 만료 후 새 예약은 다시 견적·재고 확인. 무제한 선점 남용을 제한 | 긴 대기는 결제 편의가 높지만 품절 잠금이 길어짐. 연장은 남용·경쟁 조건 증가. 10분과 계정별 동시 대기 한도는 미확정이며 PG 제약 확인 후 검토 |
| POL-06 늦은/불확실 결제 | 유효 선점이 있을 때만 확정. 만료/취소 뒤 검증된 결제 성공이 도착해도 예약을 부활시키지 않고 승인 취소/환불 또는 조치 대기로 수렴. 결과가 불명확하면 새 결제를 반복하지 않고 조회·대조 | 재고가 남으면 늦은 결제를 살리는 방식은 결제 편의를 높이지만 고객이 본 종료 상태와 충돌하고 재고 재확보·가격 재동의 문제가 생김 |
| POL-07 취소 조건·금액 | 플랫폼 공통의 단순한 초기 취소표를 사전 고지·예약에 보존. 무료 구간과 시점별 수수료/환불 구간을 명시하고 사업자 귀책·특별 사유는 별도 처리 | 체크인 전 전액 무료는 이해하기 쉽지만 공급자 손실을 반영하지 못함. 숙소별 자유 정책은 운영이 복잡하고 검증 조합 증가. 무료 기한·공제율·기준 시각·노쇼/조기퇴실 금액은 아직 미정 |
| POL-08 취소·재고·환불 시점 | 허용된 취소를 서비스가 수락하면 예약을 종료하고 재판매 가능한 미래 재고를 한 번만 반환. 환불은 별도 진행 상태로 추적. 환불 실패가 예약을 부활시키지 않음. 취소 금액이 달라지면 재동의 | PG 취소 성공 뒤에만 재고를 반환하면 금전 처리는 보수적이지만 PG 장애 동안 고객 취소와 재판매가 막힘. 접수/수락 기준과 기간 경계는 함께 확정 필요 |
| POL-09 이용·노쇼 | 담당 관리자의 체크인·체크아웃 기록으로 이용 완료. 날짜 경과 자동 완료는 하지 않음. 노쇼와 조기퇴실·상태 정정은 사유와 기록을 남김 | 날짜만으로 완료하면 편하지만 실제 미이용 리뷰를 허용하게 됨. 노쇼 판정 시각·정정 권한과 남은 밤 재판매 여부는 미정 |
| POL-10 리뷰·평점 | 이용 완료 예약당 리뷰 1개, 정수 1~5점. 완료 후 30일 내 작성/수정, 본인 삭제는 기간과 별개로 허용. 삭제 뒤 새 리뷰 재작성은 제한. 공개·유효 리뷰만 평균/개수에 반영 | 무기한 작성은 참여율이 높지만 오래된 경험이 누적됨. 삭제 후 재작성은 반복 평가 남용 가능. 작성 기간·수정·재작성 정책은 미확정 |
| POL-11 관리자·사업자 취소 | 일반 가입자는 관리자 자격을 스스로 얻지 못함. 서비스 관리자가 담당 숙소를 부여. 숙소 관리자 요청의 사업자 취소는 서비스 관리자 확인·사유 기록과 고객 전액 환불 대상으로 처리 | 숙소 관리자 즉시 강제 취소는 빠르지만 고객 피해·권한 남용 위험. 첫 버전은 추가 배상 자동화 대신 운영 조치 이력으로 다룸 |
| POL-12 탈퇴·기록 | 활성 예약·미해결 결제/환불이 있으면 탈퇴를 보류. 이후 계정 접근을 종료하고 개인정보와 거래/리뷰 기록을 구분해 삭제·비식별·보존 정책 적용 | 즉시 전체 삭제는 복구·거래 증빙을 잃고, 무기한 개인정보 보관은 불필요한 수집을 지속. 항목별 기간·리뷰 표시·권한 종료는 별도 확정 필요 |

POL-07의 공제율·예외를 임의의 숫자로 확정하지 않는다. 공개 숙박 예약 문서도 취소 가능 여부·시점·금액을 구분해 제시한다. 국내 기준은 적용 상황을 확인한 뒤 정책표를 검수해야 하므로, 현재 조사한 기준을 서비스 전체에 일괄 적용한다고 가정하지 않는다. [취소 조건의 구성](https://developers.booking.com/demand/docs/orders-api/cancellation-policies), [소비자분쟁해결기준 개정 정보](https://www.law.go.kr/admRulInfoP.do?admRulSeq=2100000270136&chrClsCd=010202&urlMode=admRulRvsInfoR).

범위 승인은 위 세부 정책의 승인이 아니다. POL-07 요율·예외, POL-09 노쇼/조기퇴실, POL-12 보존 기간 등 미정 값을 남긴 채 관련 기능의 요구사항을 완료하지 않는다.

## 4. 사용자 역할과 입력·출력

역할의 존재와 핵심 업무는 Kickoff 범위에 포함됐다. 아래 입력·출력·권한 세부는 요구사항 초안이다.

| 업무 | 주요 입력 | 확인 가능한 출력 | Validation·권한 |
| --- | --- | --- | --- |
| 회원 가입·로그인 | 계정 식별 정보·비밀번호, 필요한 동의 | 가입/인증 결과, 본인 계정 정보 | 중복 계정, 빈/잘못된 입력, 자격 실패, 탈퇴/접근 제한을 구분. 권한을 가입 입력으로 지정할 수 없음 |
| 숙소·타입 관리 | 지역·주소·명칭·설명·기본 이미지·편의 정보·입퇴실 시각, 타입 정원·수량 | 저장 결과, 판매 상태와 고객 표시 정보 | 담당 숙소 권한, 필수 정보·정원·수량·유효 이미지 참조 검사 |
| 날짜 공급·요금 | 타입·기간·날짜별 공급량/판매 상태/요금·추가 인원 금액 | 적용 내역, 충돌 날짜·거절 사유, 변경 이력 | 음수·정원/공급 초과·역전 기간 금지. 여러 날짜 변경은 부분 적용을 숨기지 않음 |
| 검색·견적 | 지역·체크인/아웃·총인원·기본 정렬/페이지, 선택 타입 | 판매 가능 상품, 숙박 전체 금액·박별 내역·취소 조건 | POL-01/02, 최대 정원, 모든 숙박일의 공급·요금·판매 상태 확인 |
| 예약·결제 | 본인·선택 상품/기간/인원·동의한 견적, 결제 의도 식별 | 예약 번호·조건·기한·현재 예약/결제 상태 | 타인 계정/금액 위변조, 변경 조건, 중복 요청, 부족 재고 차단 |

## 6. 업무 상태 전이 초안

이름은 업무 설명이며 DB Enum·테이블·API 계약이 아니다. 아래 전이와 시점은 POL 정책 검수 후 확정한다.

| 대상 | 정상 전이와 종료 | 허용하지 않는 처리 |
| --- | --- | --- |
| 예약 | 생성과 전체 날짜 선점 → 결제 대기 → 검증된 결제로 확정 → 이용 업무 연결. 대기는 취소/실패/만료로 종료, 확정은 허용된 취소로 종료 | 부분 날짜만 선점, 만료/취소 예약 자동 부활, 동일 예약 두 번 확정 |
| 결제 | 시도 → 확인 대기 → 검증된 성공 또는 명확한 실패. 불확실하면 조회/대조·조치 대기. 성공 후 취소/환불은 별도 진행/완료/실패 기록 | 응답 시간 초과를 미결제 확정으로 처리, 오래된 통지로 현재 성공 상태 덮어쓰기, 클라이언트 금액 신뢰 |
| 취소·환불 | 취소 견적 → 동의·수락 → 재고 반환과 환불 진행 추적 → 완료 또는 재처리/조치 대기 | 환불 실패로 고객 예약을 되살림, 재시도로 두 번 반환/환불, 새 요율 소급 적용 |
| 이용 | 확정 예약의 예정 이용 → 실제 체크인 → 체크아웃·완료. 미이용은 노쇼, 오입력은 추적 가능한 정정 | 시간 경과만으로 이용 완료, 취소/미확정 예약의 체크인, 미래 완료 기록 |
| 리뷰 | 자격 확인 → 작성·공개 → 허용된 수정/삭제 또는 관리자 비공개/복원 | 같은 예약의 중복 리뷰, 비공개 내용을 고객 수정만으로 자동 재공개, 삭제/숨김 리뷰를 평균에 포함 |

확정 예약의 날짜·타입·인원 변경은 첫 버전에서는 기존 예약 취소와 새 예약을 통해 처리하도록 제안한다. 가격·재고를 몰래 바꾸는 직접 수정은 허용하지 않는다. 취소 비용과 재예약 실패 위험을 안내하며 이 변경 정책도 검수 대상이다.

**계획된 검증 사례이며 실행 결과가 아니다.** POL의 미정 값은 그 값이 확정된 뒤 경계값 테스트로 구체화한다.

| AC-21 리뷰 자격·중복 | 완료 본인 예약, 타인/취소/미이용/노쇼, 기간 밖·점수 범위 밖, 동시 두 리뷰 | 유효한 1개만 작성. 다른 요청은 정해진 사유로 거절 |

AC-09의 수치는 테스트 시나리오 예시다. 구현 정책이나 운영 수용량 확정이 아니다. 동시 테스트는 초기 데이터, 시작 동기화, 독립 트랜잭션, 요청 수, 성공/거절/오류 건수와 최종 DB 상태를 남기고 인프라 오류를 재고 부족으로 위장하지 않는다.

## 8. PG-GATE — 설계 전에 확인할 외부 환경

아래는 특정 사업자의 지원 기능을 주장하는 목록이 아니라 **확인·선정 기준**이다.

| 확인 항목 | 확보할 근거와 미지원 시 처리 |
| --- | --- |
| 접근 조건·수단 | 테스트 계정·키·계약 필요 여부, 지원 결제수단, 서버/브라우저 절차, 테스트 데이터와 외부 접속 조건 확인 |
| 승인·조회·취소 | 실제 테스트 환경에서 가능한 작업과 응답/식별자·금액·부분 취소 제약 확인. 첫 버전 업무가 불가능하면 다른 PG 또는 범위를 사용자와 재검토 |
| 알림·정당성 | 해당 결제수단이 어떤 이벤트를 실제 보내는지, 재전송·순서·인증 검증 방법 확인. 없는 웹훅·서명을 가정하지 않으며 지원 조회/대조 등의 대안을 검토 |
| 만료·멱등·불확실 | PG의 시간 제한과 서비스 선점 기한을 구분. 재시도·멱등·취소/조회 가능 상태·일관성 지연을 확인한 뒤 연동 계약 정의 |
| 실제 검증과 모의 검증 | 실제 PG에서 확인한 정상/실패 결과와 모의로만 재현한 지연·중복·응답 유실을 분리 기록. 라이브 키·실금전 거래는 사용하지 않음 |

미지원 기능을 Mock으로 채운 뒤 PG 연동이 완료됐다고 보고하지 않는다. PG 상태를 서비스 상태와 일대일 대응한다고 미리 가정하지 않는다. 이 단계에서는 PG를 선정하거나 연동 코드를 만들지 않는다.

## 9. 누락·충돌 Review와 완료 조건

| Kickoff 핵심 범위 | 연결 요구사항·검증 |
| --- | --- |
| 타입별 다수/날짜 재고·공급 운영 | SUP-01~04, BOOK-01~03, AC-03~05/09~12 |
| 검색·기간/인원별 가격·계약 보존 | FIND-01, PRICE-01/02, AC-04/06/07 |
| 예약·결제·만료·취소·환불 | BOOK-01~04, PAY-01~04, CANCEL-01~04, AC-07~19/24 |
| 역할·권한·운영·무결성 | AUTH-01~03, DATA-01, OPS-01, ERROR-01, INV-01~08, AC-02/19/23/24 |
| 실제 이용·리뷰·평점 | STAY-01/02, REVIEW-01~03, AC-20~23 |
| 실제 DB·통합 검증·웹서비스 Lifecycle | VERIFY-01, WEB-01, RELEASE-01, AC-09~15/24/25 |

다음 항목을 요구사항 완료 전에 닫는다.

- POL-01~12의 채택/수정과 날짜·인원·가격·취소·이용·리뷰·보존 정책의 필수 값 확정. 여러 날짜 관리 변경과 예약 수정 방침도 포함.
- 입력 범위/필수 정보, 예상 오류와 사용자 안내, 취소/이용/예외 상태 전이의 충돌 해소.
- 특히 취소 수수료표·노쇼/조기퇴실·탈퇴/보존은 구조 승인만으로 숫자·예외까지 확정하지 않음.
- 각 Business Rule의 정상·실패·시간 경계·권한·동시성 수용 기준과 예상 DB 결과를 검수.
- PG는 기능을 가정하지 않고 PG-GATE의 증거를 설계 단계에서 확보할 작업으로 인계. 그 전 기능별 구현 계약은 확정하지 않음.
- 첫 Backend 기능을 선택할 정도로 요구사항이 명확한지 확인하고, 충족한 후 초기 설계로 진행.

현재는 문서 초안 준비와 검수 단계다. 자동화된 링크/범위 검사와 자체 Review는 문서 품질 검증이며 위 기능 Test의 실행 결과를 대신하지 않는다.
